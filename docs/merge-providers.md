# Native merge protection

Merge automation starts disabled and in dry run. Use a repository administrator’s authorized installation or service account. Configure HTTPS for both the forge API and web URLs. Triage authenticates its first repository read even in dry run and rejects HTTP before loading credentials. A development forge configured with `allow_http` needs HTTPS on both URLs to enable triage or resume reconciliation of an outstanding approval or merge. The adapter reads current provider state before each action. An eligible dry run publishes neither a merge request to the provider nor a successful eligibility check. [Configure repository policy](merge-policy.md).

## Optional approval

With an enabled policy and `autoApprove = true`, Razbor may cast one real vote on the reviewed revision. Leave `dryRun = true` to use approval without scheduling native merges. The provider must confirm the repository, author, revision, default destination, discussions and checks. A PR that Razbor escalated to human review stays in the human workflow. Razbor checks for an existing queue entry or native merge schedule before voting. An independent integration can still schedule a merge concurrently or react to the vote.

- **GitHub.** Use an installed GitHub App with pull-request write access and read access to the checks and protection settings. The destination must report that the App can dismiss its reviews. Configure enforced stale-review dismissal on the destination, or lock the source branch against changes. Razbor submits the PR node ID and reviewed commit OID and verifies the returned review. It checks the App’s recent reviews first, then reads older pages as needed to identify its latest approval, dismissal or change request on the reviewed commit. If the available history cannot establish whether a vote already exists, Razbor withholds a new vote. A missing human approval alone allows Razbor to cast its own vote. [GitHub pull request reviews](https://docs.github.com/en/graphql/reference/pulls#addpullrequestreviewinput) · [GitHub branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).
- **GitLab.** Use a bot account eligible to approve and a project exposing the approval configuration API. Enable full approval reset on push, disable selective Code Owner resets and leave merge trains off. Razbor submits to the numeric project and MR with the reviewed SHA. GitLab’s approval list identifies voters without reporting the SHA of their vote. After a lost response Razbor keeps the vote unconfirmed unless it can establish the outcome. [GitLab approval configuration and SHA precondition](https://docs.gitlab.com/api/merge_request_approvals/).
- **Forgejo.** Dry runs publish the confidence report. The supported Forgejo API cannot guarantee that an approval applies only to the requested revision, so Razbor reports native approval as unavailable.

On GitHub, `requirePassingChecks` also governs optional CI. With it enabled, Razbor waits for a positive CI result and checks all reported runs and commit statuses. With it disabled, a failure or pending status unrelated to any required check can coexist with an approval. GitHub’s required check names and App restrictions still apply on the reviewed commit. When GitHub requires both a Check Run and a commit status with the same name, both must pass. An App-pinned legacy status can satisfy the requirement when GitHub marks it required and Razbor verifies its bot account and the expected App ID. If a ruleset requires a workflow whose result Razbor cannot identify, auto-approval waits and the console directs a maintainer to verify the rule in GitHub. [GitHub required status checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).

Razbor records a vote intent before submission. A later human escalation starts withdrawal of the bot’s vote even on the same source commit. Policy changes, source changes and repository deletion settle previous votes before committing. The human escalation comment identifies an unconfirmed withdrawal. Until the forge confirms it, a maintainer should treat the old vote as potentially active and obtain a separate human review. An outstanding withdrawal blocks new Razbor votes on every head of that PR or MR.

On GitHub, withdrawal targets the immutable review ID and verifies the bot, reviewed commit, marker and PR. On GitLab, dedicate the bot account on this project to one Razbor repository connection. A second connection, another deployment or a script sharing that account can change its vote outside this dispatcher’s locks. Enable auto-approval only with this ownership in place. Unapproval targets the authenticated bot on the MR. Razbor withdraws a previously acknowledged vote on its original head and verifies the response. A lost submission or withdrawal can require operator confirmation because GitLab's vote list identifies the account without the revision or request ID. [GitHub review dismissal](https://docs.github.com/en/graphql/reference/pulls#dismisspullrequestreview) · [GitLab unapproval](https://docs.gitlab.com/api/merge_request_approvals/#unapprove-a-merge-request).

**Recovering an unconfirmed withdrawal.** Drain all dispatchers and pause policy changes for the repository. Record the old bot ID, numeric project and PR, public review ID and reviewed head in a restricted incident record. Use provider-side request records to establish that every prior vote and withdrawal has completed or was definitively rejected. Verify the original vote has been dismissed or is absent. Once both facts are established, a database operator can replace that exact review’s `forge_approval` with `{"botId":"<original bot ID>","status":"dismissed"}` under repository and PR row locks, requiring the saved bot, head and withdrawal intent to match. Set the PR’s `merge_after` to `now()` in the same transaction, record the intervention and resume the dispatcher. If the provider cannot establish the outcome, retain the pending withdrawal; a confirmed terminal merge can also settle it.

## GitHub

Razbor supports confidence reports, reviewer escalation and opt-in approvals. Complete the final merge in GitHub. GitHub attaches a check run to a commit and updates it by check-run ID. That update accepts no condition on the owner of a PR's current auto-merge request. Razbor therefore reports `github_schedule_owner_unbound` and never creates or releases an eligibility check for a new merge. [GitHub check runs](https://docs.github.com/en/rest/checks/runs#update-a-check-run) · [GitHub auto-merge permissions](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request).

**Upgrading from a preview with native GitHub scheduling.** Keep the App's Checks write permission and existing protections while retiring prior requests. Razbor inspects the saved PR, head, App and review identifier. It can cancel its earlier eligibility check and confirm the result. A lost submission or check release can still be in flight. GitHub's disable-auto-merge mutation also lacks an ownership precondition, so a maintainer must inspect and disable a remaining schedule in GitHub. Follow the recovery procedure below for unconfirmed operations. [GitHub auto-merge mutation inputs](https://docs.github.com/en/graphql/reference/pulls#disablepullrequestautomergeinput).

Once all earlier authorizations are settled, remove the preview's required **Razbor / merge eligibility** check from your branch protection or dedicated ruleset. Leaving it required can block human merges because Razbor no longer publishes a passing result. Keep the repository's ordinary CI, discussion and human-review protections in place.

## GitLab

Native scheduling requires the Projects API to expose `merge_trains_enabled: false`. GitLab 17.11 Community Edition omits this field, so Razbor reports `unsupported_gitlab_merge_strategy` there. [GitLab 17.11 project serializer](https://github.com/gitlabhq/gitlabhq/blob/v17.11.7/lib/api/entities/project.rb). Other 17.11 installations must provide the field and the protections below. On 18.x and 19.x it additionally requires the Projects API to return `automatic_rebase_enabled: false`. GitLab documents this read field from 19.4. [GitLab Projects API](https://docs.gitlab.com/api/projects/#retrieve-a-project). Use a project bot with an API token and the **Developer** role. The API credential must be able to read the version, project settings, protected branch rules, commit, and MR pipeline.

- Protect the default branch by exact name. Grant the bot merge access there. Protect all other branches with a `*` rule denying push and merge to this bot. For instance, allow Maintainers on non-default branches and grant specific human users access where needed. Every additional rule must also exclude the bot from other destinations. The check rejects ambiguous group, custom-role and deploy-key allowances, and requires force pushes disabled across those rules.
- Choose **Merge commit with semi-linear history** or **Fast-forward merge**. Disable merge trains and automatic rebase before merge. The adapter also requires explicit evidence that merge trains are disabled. Use a reviewed source commit whose only parent is the reviewed target tip.
- Require successful pipelines and disable the option that accepts skipped pipelines. Razbor checks for a successful pipeline on the exact MR SHA, resolved blocking discussions, and GitLab’s `mergeable` status. These native gates also apply when `requirePassingChecks` is off. Select squash in Razbor when the project permits squash. For an unsquashed merge, select semi-linear history, set the project squash option to **Do not allow**, and verify that the MR reports `squash_on_merge: false`. GitLab can keep an existing squash preference when the merge request sends `squash: false`. [GitLab merge endpoint implementation](https://github.com/gitlabhq/gitlabhq/blob/v17.11.7/lib/api/merge_requests.rb#L700-L706). The rebase method is unavailable.

After validation, Razbor sends `PUT /projects/:id/merge_requests/:iid/merge` to the numeric project ID with `auto_merge: true`, the reviewed `sha`, and the chosen `squash` setting. GitLab cancels on new source commits. Semi-linear or fast-forward merging with automatic rebase off also guards target updates. GitLab stores the scheduling user when enabling auto-merge. Its API permits a null `merge_user`. Razbor accepts null only for a directly acknowledged PUT that identifies the exact project, MR, head and destination and reports an active native schedule. The dispatcher commits the acknowledgement before re-reading the MR. Without this receipt, an unattributed schedule stays fenced. An explicit different actor always requires intervention. [GitLab 17.11 scheduler](https://github.com/gitlabhq/gitlabhq/blob/v17.11.7/app/services/auto_merge/base_service.rb#L97-L109) · [GitLab 17.11 MR serializer](https://github.com/gitlabhq/gitlabhq/blob/v17.11.7/lib/api/entities/merge_request_basic.rb#L4-L10). Its cancel API has no atomic schedule-owner precondition. Settle a pending request in GitLab before changing policy or starting a replacement review when Razbor reports that cancellation requires intervention. [GitLab MR API](https://docs.gitlab.com/api/merge_requests/#merge-a-merge-request) · [GitLab auto-merge and revision changes](https://docs.gitlab.com/user/project/merge_requests/auto_merge/#pipeline-success-for-auto-merge) · [GitLab merge methods](https://docs.gitlab.com/user/project/merge_requests/methods/).

An active GitLab schedule and its current merge checks are shown separately. If the reviewed pipeline starts running again, fails, or a conflict or blocking discussion appears, the PR stays scheduled and displays the current wait or block. Razbor rechecks the existing request. It does not submit it a second time.

## Forgejo

Repository policy, assessments, triage, reviewer lookups and durable comments are supported. Native scheduling returns `forgejo_schedule_does_not_pin_reviewed_head` and sends no merge mutation.

In the verified 15.0.12 API, `POST /repos/{owner}/{repo}/pulls/{index}/merge` accepts `head_commit_id` and `merge_when_checks_succeed`. Scheduling takes a separate path even when current checks pass. Its stored record contains the PR ID, scheduling user and merge options. The worker checks the latest queued SHA and invokes the eventual merge with an empty expected head. The 17.0.2 worker has the same behavior. A protected target and passing required checks do not bind this operation to Razbor’s reviewed commit. Continue using Forgejo’s normal protected-branch checks and human merge workflow. [Forgejo 15.0.12 API handler](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.12/routers/api/v1/repo/pull.go) · [Stored schedule](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.12/models/pull/automerge.go) · [15.0.12 worker](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.12/services/automerge/automerge.go) · [17.0.2 worker](https://codeberg.org/forgejo/forgejo/src/tag/v17.0.2/services/automerge/automerge.go).

## Resolving an unacknowledged write

A saved `prepared` step can retire offline because no provider mutation has begun. A saved `creating_check` step requires GitHub readback because the Check Run POST may still arrive. An empty check list leaves the review fenced. If the provider establishes definitive non-delivery and the check can no longer arrive, use the audited operator procedure below. After submission, an observed owned schedule, its acknowledged removal, or a provider-confirmed terminal merge can settle the fence automatically. A terminal merge of a different revision retires the obsolete authorization as stale. Current open-state reads, elapsed time and restarting Razbor cannot prove an earlier submission or eligibility release finished.

For an open PR that remains fenced after a lost write, an authorized provider administrator and Razbor database operator can reconcile the specific operation using the following procedure.

1. Stop and drain every dispatcher writing to this repository. Record the numeric provider project and PR, the public review ID, the saved step, head, target and the automation identity in a restricted incident record.
2. Establish a definitive outcome for the outstanding provider request. Obtain provider-side request or worker records confirming completion, rejection, or that the operation was never admitted and can no longer arrive. For a delayed request, arrange with the provider operator to fence the old credentials, drain in-flight work and account for previously authorized background jobs. Revoking a token alone does not prove that already accepted work has stopped. If the operator cannot establish that the old write can no longer take effect, keep the fence. The provider can still confirm a terminal merge later.
3. Inspect the exact PR. If it already merged, let the dispatcher reconcile the terminal result. Otherwise remove any old native authorization in the provider, verify there is no active native request, and on GitHub look up the eligibility Check Run by App, external ID and head. If it exists, revoke it and verify the resulting status. A fresh installation token restricted to Checks write can revoke the old App-owned check while merge credentials remain disabled. For a `creating_check` request with confirmed non-delivery, record the provider’s evidence that the POST can no longer arrive and verify the absence of both a matching Check Run and a native schedule. Record the provider evidence, responsible operator and verification time in the incident. Keep credentials disabled until the database transaction commits.
4. Use an authorized maintenance session in `psql`. Supply the independently verified review ID, full reviewed SHA and incident reference with the `review_id`, `head_sha` and `incident` variables. The existing decision-history trigger records the maintenance identity and incident reference. Keep tokens and raw provider payloads out of this field.

```sql
BEGIN;
SELECT p.id FROM repositories p
JOIN reviews r ON r.repository_id = p.id
WHERE r.public_id = :'review_id' FOR UPDATE OF p;
SELECT p.id FROM pull_requests p
JOIN reviews r ON r.merge_pull_request_id = p.id
WHERE r.public_id = :'review_id' FOR UPDATE OF p;

WITH settled AS (
  UPDATE reviews SET merge_action = 'refused',
    merge_decision = jsonb_build_object(
      'status', 'stale', 'reviewers', '[]'::jsonb,
      'reasons', jsonb_build_array(jsonb_build_object(
        'code', 'operator_resolved',
        'message', format('Native authority retired by %s after provider verification (%s).',
                          session_user, :'incident'::text))))
  WHERE public_id = :'review_id' AND head_sha = :'head_sha'
    AND merge_action IN ('writing', 'uncertain', 'scheduled')
    AND length(trim(:'incident')) BETWEEN 1 AND 128
  RETURNING merge_pull_request_id
)
UPDATE pull_requests SET merge_after = now()
WHERE id IN (SELECT merge_pull_request_id FROM settled)
RETURNING public_id;
```

Commit only when the returned PR is the intended one. Otherwise roll back and recheck the identifiers and evidence. Restore approved credentials and resume the dispatcher. The retired review remains refused. A new review must pass all current policy and provider guards.
