# Native merge protection

Merge automation starts disabled and in dry run. Use a repository administrator’s authorized installation or service account. The adapter reads current provider state before each action. An eligible dry run publishes neither a merge request to the provider nor a successful eligibility check. [Configure repository policy](merge-policy.md).

## GitHub

Guarded GitHub auto-merge requires an organization-owned repository with classic push restrictions available on its plan. Personal repositories can use Razbor’s human triage. [GitHub branch restrictions](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches#restrict-who-can-push-to-matching-branches).

Install the GitHub App on the target repository. For an existing App, update its repository permissions to **Contents — Read and write**, **Checks — Read and write** and **Administration — Read-only**. Keep the existing pull request and issue write permissions. Installation owners must approve the permission upgrade. New manifests request these permissions. Tokens delivered to Git source readers are scoped to read-only contents in one bound repository. Installation repository discovery uses read-only metadata. Only the server requests the installation privileges needed for review and merge operations. Razbor resolves the numeric App ID separately from its bot account ID. [GitHub installation permission upgrades](https://docs.github.com/en/apps/maintaining-github-apps/modifying-a-github-app-registration#changing-the-permissions-of-a-github-app).

1. Enable **Allow auto-merge** and the chosen merge method in the repository.
2. Give the default branch an exact classic branch protection rule. Enforce it for administrators, disable force pushes and deletions, and require branches to be up to date before merging. Enable **Require conversation resolution before merging**, either on this protection or in an active pull request ruleset for the default branch that the App cannot bypass. GitHub then enforces a thread reopened after Razbor’s final audit. Configure the repository’s CI and human approvals there. With `requirePassingChecks` on, Razbor needs a successful configured check run in addition to its own gate.
3. Create a separate, active branch ruleset for the default branch requiring **Razbor / merge eligibility** with this GitHub App as its expected source. Configure only the eligibility requirement in this ruleset. For repositories with human maintainers, give the authorized team the provider’s **For pull requests only** bypass for this dedicated ruleset. Their usual approvals and CI remain enforced by the separate branch protection. The installation itself must have no bypass. Use the exact name and numeric App ID in the rules API when bootstrapping a check before its first run. [GitHub rulesets and bypass modes](https://docs.github.com/en/rest/repos/rules).
4. Restrict the App’s merge permission to the default branch. Configure a classic catch-all rule `**/*` with administrator enforcement and push restrictions excluding the App. Every other non-default rule must also exclude the App, or lock that branch. Give humans the appropriate user or team push allowances for their ordinary branches.
5. For a branch intended for automated merge, freeze its same-repository source branch with classic **Lock branch**, administrator enforcement, and disabled fork syncing, force pushes and deletions. Submit a head whose only parent is the reviewed default-branch tip. This lets strict branch protection detect target movement while the source stays immutable. The adapter never changes these protections for the operator. [GitHub branch protection options](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

The adapter also recognizes the App-pinned eligibility check on the default branch’s classic protection. This alternative makes the check mandatory for **human merges too**. Escalated, disabled and dry-run reviews do not produce a passing check, so this configuration can prevent maintainers from merging those PRs. Use the separate ruleset above where humans must retain their governed merge workflow.

Razbor creates a pending Check Run for the exact head, arms `enablePullRequestAutoMerge` with the reviewed `expectedHeadOid`, revalidates the PR, and releases only the check run whose App, PR, review and base match. It requires the App to own the armed request. The source lock addresses later pushes by repository writers, the exclusive target permission addresses retargeting, and the PR-specific write fence prevents a passing check from authorizing a separate bot request. Queue targets, forks, mutable source branches, and checks whose successful completion cannot be verified are unsupported. Status-only CI contexts can remain awaiting checks until represented by a successful required Check Run. The adapter bounds its inspection to 100 classic protections, 100 allowances per inspected rule, 100 open PRs and 100 latest check runs. It verifies that the reviewed head is unique across the open PRs before releasing a commit-wide Check Run. [GitHub GraphQL mutation](https://docs.github.com/en/graphql/reference/pulls#enablepullrequestautomergeinput) · [GitHub native auto-merge behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/automatically-merging-a-pull-request).

Before each provider mutation the dispatcher commits its current step. A restart can continue from a pending check created for this review, or from an observed App-owned native request when the saved step proves no eligibility release was attempted. A confirmed GitHub rate limit defers the rejected submission until the provider’s retry time. Without a retry or reset header Razbor waits at least one minute. The pending check can resume under the current policy when the wait ends. [GitHub rate limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#exceeding-the-rate-limit). A lost success PATCH is observed until it finishes. Razbor sends at most one success PATCH for a review. Rows created before these checkpoints retain the conservative recovery behavior.

Withdrawing an acknowledged authorization cancels and verifies the exact App-owned check. GitHub’s disable-auto-merge mutation takes a PR ID and lacks an ownership precondition. When an active native request remains, a maintainer inspects it and disables it in GitHub. Razbor retains the fence until it reads the native request as absent. When a review is replaced during check creation, Razbor waits for the exact App-owned pending check, cancels it and renames it to **Razbor / retired merge eligibility** in one update. It verifies the check’s ID, head, App, review identifier, name and conclusion and confirms native auto-merge is off. A replacement review can then create its own required check on the same head. A new review can also retire a visible pending check left by a definitively rejected native submission, or by the original preview’s offline retirement at `creating_check`. Razbor verifies the saved reason, the earlier review’s identity, PR, head and base, and the absence of a native request. It repeats all provider checks before scheduling the replacement. Other active checks and previously released eligibility checks still block reuse. [GitHub Check Run updates](https://docs.github.com/en/rest/checks/runs#update-a-check-run). [GitHub auto-merge mutation inputs](https://docs.github.com/en/graphql/reference/pulls#disablepullrequestautomergeinput).

## GitLab

The adapter supports GitLab 17.11 with the protections below. On 18.x and 19.x it additionally requires the Projects API to return `automatic_rebase_enabled: false`. GitLab documents this read field from 19.4. [GitLab Projects API](https://docs.gitlab.com/api/projects/#retrieve-a-project). Use a project bot with an API token and the **Developer** role. The API credential must be able to read the version, project settings, protected branch rules, commit, and MR pipeline.

- Protect the default branch by exact name. Grant the bot merge access there. Protect all other branches with a `*` rule denying push and merge to this bot. For instance, allow Maintainers on non-default branches and grant specific human users access where needed. Every additional rule must also exclude the bot from other destinations. The check rejects ambiguous group, custom-role and deploy-key allowances, and requires force pushes disabled across those rules.
- Choose **Merge commit with semi-linear history** or **Fast-forward merge**. Disable merge trains and automatic rebase before merge. The adapter also requires explicit evidence that merge trains are disabled. Use a reviewed source commit whose only parent is the reviewed target tip.
- Require successful pipelines and disable the option that accepts skipped pipelines. Razbor checks for a successful pipeline on the exact MR SHA, resolved blocking discussions, and GitLab’s `mergeable` status. These native gates also apply when `requirePassingChecks` is off. Select squash in Razbor when the project permits squash. For an unsquashed merge, select semi-linear history, set the project squash option to **Do not allow**, and verify that the MR reports `squash_on_merge: false`. GitLab can keep an existing squash preference when the merge request sends `squash: false`. [GitLab merge endpoint implementation](https://github.com/gitlabhq/gitlabhq/blob/v17.11.7/lib/api/merge_requests.rb#L700-L706). The rebase method is unavailable.

After validation, Razbor sends `PUT /projects/:id/merge_requests/:iid/merge` to the numeric project ID with `auto_merge: true`, the reviewed `sha`, and the chosen `squash` setting. GitLab cancels on new source commits. Semi-linear or fast-forward merging with automatic rebase off also guards target updates. GitLab stores the scheduling user when enabling auto-merge. Its API permits a null `merge_user`. Razbor accepts null only for a directly acknowledged PUT that identifies the exact project, MR, head and destination and reports an active native schedule. The dispatcher commits the acknowledgement before re-reading the MR. Without this receipt, an unattributed schedule stays fenced. An explicit different actor always requires intervention. [GitLab 17.11 scheduler](https://github.com/gitlabhq/gitlabhq/blob/v17.11.7/app/services/auto_merge/base_service.rb#L97-L109) · [GitLab 17.11 MR serializer](https://github.com/gitlabhq/gitlabhq/blob/v17.11.7/lib/api/entities/merge_request_basic.rb#L4-L10). Its cancel API has no atomic schedule-owner precondition. Settle a pending request in GitLab before changing policy or starting a replacement review when Razbor reports that cancellation requires intervention. [GitLab MR API](https://docs.gitlab.com/api/merge_requests/#merge-a-merge-request) · [GitLab auto-merge and revision changes](https://docs.gitlab.com/user/project/merge_requests/auto_merge/#pipeline-success-for-auto-merge) · [GitLab merge methods](https://docs.gitlab.com/user/project/merge_requests/methods/).

## Forgejo

Repository policy, assessments, triage, reviewer lookups and durable comments are supported. Native scheduling returns `forgejo_schedule_does_not_pin_reviewed_head` and sends no merge mutation.

In the verified 15.0.12 API, `POST /repos/{owner}/{repo}/pulls/{index}/merge` accepts `head_commit_id` and `merge_when_checks_succeed`. Scheduling takes a separate path even when current checks pass. Its stored record contains the PR ID, scheduling user and merge options. The worker checks the latest queued SHA and invokes the eventual merge with an empty expected head. The 17.0.2 worker has the same behavior. A protected target and passing required checks do not bind this operation to Razbor’s reviewed commit. Continue using Forgejo’s normal protected-branch checks and human merge workflow. [Forgejo 15.0.12 API handler](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.12/routers/api/v1/repo/pull.go) · [Stored schedule](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.12/models/pull/automerge.go) · [15.0.12 worker](https://codeberg.org/forgejo/forgejo/src/tag/v15.0.12/services/automerge/automerge.go) · [17.0.2 worker](https://codeberg.org/forgejo/forgejo/src/tag/v17.0.2/services/automerge/automerge.go).

## Resolving an unacknowledged write

A saved `prepared` step can retire offline because no provider mutation has begun. A saved `creating_check` step requires GitHub readback because the Check Run POST may still arrive. An empty check list leaves the review fenced. If the provider establishes definitive non-delivery and the check can no longer arrive, use the audited operator procedure below. After submission, an observed owned schedule, its acknowledged removal, or a provider-confirmed terminal merge can settle the fence automatically. A terminal merge of a different revision retires the obsolete authorization as stale. Current open-state reads, elapsed time and restarting Razbor cannot prove an earlier submission or eligibility release finished.

For an open PR that remains fenced after a lost write, an authorized provider administrator and Razbor database operator can reconcile the specific operation using the following procedure.

1. Stop and drain every dispatcher writing to this repository. Record the numeric provider project and PR, the public review ID, the saved step, head, target and the automation identity in a restricted incident record.
2. Establish a definitive outcome for the outstanding provider request. Obtain provider-side request or worker records confirming completion, rejection, or that the operation was never admitted and can no longer arrive. For a delayed request, arrange with the provider operator to fence the old credentials, drain in-flight work and account for previously authorized background jobs. Revoking a token alone does not prove that already accepted work has stopped. If the operator cannot establish that the old write can no longer take effect, keep the fence. The provider can still confirm a terminal merge later.
3. Inspect the exact PR. If it already merged, let the dispatcher reconcile the terminal result. Otherwise remove any old native authorization in the provider, verify there is no active native request, and on GitHub revoke and verify the old eligibility Check Run by App, external ID and head. A fresh installation token restricted to Checks write can revoke the old App-owned check while merge credentials remain disabled. Record the provider evidence, responsible operator and verification time in the incident. Keep credentials disabled until the database transaction commits.
4. Use an authorized maintenance session in `psql`. Supply the independently verified review ID, full reviewed SHA and incident reference with the `review_id`, `head_sha` and `incident` variables. The existing decision-history trigger records the maintenance identity and incident reference. Keep tokens and raw provider payloads out of this field.

```sql
BEGIN;
SELECT p.id FROM repositories p
JOIN reviews r ON r.repository_id = p.id
WHERE r.public_id = :'review_id' FOR UPDATE OF p;
SELECT p.id FROM pull_requests p
JOIN reviews r ON r.merge_pull_request_id = p.id
WHERE r.public_id = :'review_id' FOR UPDATE OF p;

WITH settled AS (
  UPDATE reviews SET merge_action = 'refused',
    merge_decision = jsonb_build_object(
      'status', 'stale', 'reviewers', '[]'::jsonb,
      'reasons', jsonb_build_array(jsonb_build_object(
        'code', 'operator_resolved',
        'message', format('Native authority retired by %s after provider verification (%s).',
                          session_user, :'incident'::text))))
  WHERE public_id = :'review_id' AND head_sha = :'head_sha'
    AND merge_action IN ('writing', 'uncertain', 'scheduled')
    AND length(trim(:'incident')) BETWEEN 1 AND 128
  RETURNING merge_pull_request_id
)
UPDATE pull_requests SET merge_after = now()
WHERE id IN (SELECT merge_pull_request_id FROM settled)
RETURNING public_id;
```

Commit only when the returned PR is the intended one. Otherwise roll back and recheck the identifiers and evidence. Restore approved credentials and resume the dispatcher. The retired review remains refused. A new review must pass all current policy and provider guards.
